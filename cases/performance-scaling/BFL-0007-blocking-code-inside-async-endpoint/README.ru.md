# Блокирующий код внутри async endpoint

## Краткое описание

FastAPI endpoint объявлен через `async def`, но внутри обработчика вызывается блокирующий код.

Endpoint выглядит асинхронным, но `time.sleep()` блокирует event loop. Когда несколько запросов приходят одновременно, они обрабатываются один за другим, а не выполняются параллельно по ожиданию.

## Проблема

В API есть endpoint, который имитирует медленную работу.

Сломанная реализация написана как async endpoint:

```python
@app.get("/slow-operation")
async def slow_operation():
    time.sleep(0.08)
    return {"status": "done"}
```

Самого `async def` недостаточно. Блокирующий вызов всё равно выполняется в потоке event loop, поэтому event loop не может переключиться на другие запросы, пока работает `time.sleep()`.

## Почему это происходит в production

Такой баг часто встречается у разработчиков, которые начинают использовать FastAPI и думают, что любой endpoint с `async def` автоматически становится неблокирующим.

На практике async помогает только тогда, когда код внутри корутины сотрудничает с event loop. `time.sleep()`, синхронные HTTP-клиенты, медленные файловые операции и тяжёлые вычисления всё равно могут заблокировать остальные корутины на том же event loop.

## Сценарий бага

1. Три клиента одновременно отправляют `GET /slow-operation`.
2. Endpoint начинает обрабатывать первый запрос.
3. Endpoint вызывает `time.sleep()`.
4. Event loop заблокирован и не может продвигать остальные запросы.
5. Запросы завершаются примерно один за другим.

## Сломанная реализация

Сломанная реализация блокирует выполнение внутри async endpoint:

```python
time.sleep(WORK_SECONDS)
```

Эта строка останавливает весь поток event loop. Она не останавливает только текущий запрос.

## Где именно происходит ошибка

Ошибка происходит на границе между async-обработчиком запроса и синхронной блокирующей работой.

`async def` создаёт корутину, но не делает все функции внутри неё асинхронными автоматически. Если код вызывает блокирующую функцию, event loop не сможет выполнять другие запланированные задачи, пока эта функция не вернёт управление.

## Как отлавливать такую ошибку

Тест с одним запросом обычно не ловит эту проблему, потому что один запрос всё равно успешно возвращает ответ.

Лучше отправить несколько запросов одновременно и измерить общее время. Если три запроса занимают примерно в три раза больше времени, чем один запрос, endpoint скорее всего блокирует event loop.

Такому тесту не нужна точная production-метрика. Он должен доказать форму ошибки: параллельные запросы ведут себя как последовательные.

## Падающий тест

Падающий тест отправляет три concurrent requests на `GET /slow-operation`.

Безопасное поведение: общее время остаётся близким к одной искусственной задержке, потому что все запросы должны ожидать одновременно.

Сломанная реализация использует `time.sleep()`, поэтому запросы выполняются почти один за другим и тест падает.

## Диагностика

Система ломается, потому что блокирующий код выполняется прямо на event loop.

Event loop отвечает за переключение между ожидающими async-задачами. Когда задача вызывает `time.sleep()`, поток event loop занят и не может переключиться на другие запросы.

В результате страдает конкурентность: сервис может выглядеть нормально при одном запросе, но задержки быстро растут, когда одновременно приходит несколько запросов.

## Исправленная реализация

Исправленная реализация использует неблокирующее ожидание:

```python
await asyncio.sleep(WORK_SECONDS)
```

`asyncio.sleep()` сообщает event loop, что эта корутина ждёт и её можно поставить на паузу. Пока она ждёт, event loop продолжает обрабатывать другие запросы.

Если реальная работа блокирующая и её нельзя заменить async-библиотекой, короткие блокирующие I/O-операции можно вынести в thread pool, а долгую работу — в background job. Главное правило: event loop не должен выполнять блокирующую работу напрямую.

## Заметки для production

Блокирующий код в async endpoints может приводить к timeout, накоплению очереди запросов и непредсказуемой задержке под нагрузкой.

Частые источники проблемы: `time.sleep()`, синхронные database drivers, синхронные HTTP-клиенты, медленные файловые операции, обработка изображений и тяжёлые вычисления.

Для I/O лучше использовать async-совместимые библиотеки, если весь стек вокруг асинхронный. Если блокирующей работы не избежать, изолируй её через thread pool или выноси из request path.

## Компромиссы

`await asyncio.sleep()` — правильный фикс для этого lab case, потому что медленная работа здесь только имитируется.

В реальных системах замена блокирующего клиента на async-клиент может требовать больше изменений, но это сохраняет масштабируемость обработки запросов.

Thread pool может быть практичным решением для небольших блокирующих операций, но это не бесплатная масштабируемость. Долгую CPU-heavy работу обычно лучше выносить в worker process или background job.
