# Retry без идемпотентности создаёт дубли заказов

## Краткое описание

Пользователь создаёт заказ, та же операция повторяется, и backend создаёт второй заказ.

Ошибка не в JSON-ответе и не в validation. Ошибка в том, что backend воспринимает повтор как новую команду.

## Metadata

- ID: `BFL-0003`
- Category: `idempotency-consistency`
- Secondary category: `queues-background-jobs`
- Level: `junior-middle`
- Technologies: `python`, `fastapi`, `postgresql`, `sqlalchemy`, `pytest`
- Failure modes: `duplicate-processing`
- Patterns: `idempotency-key`
- Status: `released`

## Проблема

В API есть endpoint:

```http
POST /orders
```

Клиент отправляет запрос с заголовком `Idempotency-Key`. Если клиент повторяет ту же операцию с тем же ключом, backend должен вернуть тот же заказ, а не создавать дубль.

Сломанная реализация принимает ключ, но не использует его, чтобы распознать повтор.

## Почему это происходит в production

Повторы запросов — нормальная часть production-систем. Они могут приходить от HTTP-клиентов, load balancer, webhook-отправителей, background jobs или workers после timeout.

Без идемпотентности повтор может повторить побочный эффект. Для orders и payments это может означать дубли заказов, повторные списания, повторные письма или лишние background jobs.

## Сценарий бага

1. Клиент отправляет `POST /orders` с `Idempotency-Key: same-command`.
2. Backend создаёт заказ `#1`.
3. Клиент повторяет тот же запрос с тем же ключом.
4. Backend создаёт заказ `#2`.
5. Одно действие пользователя создало два заказа.

## Сломанная реализация

Сломанный endpoint проверяет, что `Idempotency-Key` есть, а потом каждый раз создаёт новый заказ:

```python
order = create_order(payload=payload, idempotency_key=idempotency_key)
```

В `broken/repository.py` функция `create_order()` всегда вставляет новую строку. Idempotency key сохраняется, но никогда не используется для поиска уже созданного заказа.

## Где именно происходит ошибка

Ошибка происходит перед вставкой в базу.

У backend уже есть вся информация, чтобы распознать повтор: в запросе есть `Idempotency-Key`. Не хватает шага, который проверяет, существует ли заказ с таким ключом, до создания новой строки.

Опасный паттерн:

```python
receive command
insert row
return row
```

Более безопасный паттерн:

```python
receive command
find existing row by idempotency key
if found: return existing row
else: insert row
```

## Как отлавливать такую ошибку

Нужен тест, который отправляет одну и ту же команду два раза.

Недостаточно проверить, что оба ответа успешные. Нужно проверить, что второй ответ возвращает тот же заказ, а в базе остался только один заказ.

Именно это ловит production-проблему: повторное выполнение меняет состояние второй раз.

## Падающий тест

Падающий тест дважды отправляет одинаковый `POST /orders` с одним и тем же `Idempotency-Key`.

Безопасное поведение:

- оба ответа относятся к одному и тому же заказу;
- в базе ровно один заказ.

Сломанная реализация создаёт два заказа, поэтому тест падает.

## Диагностика

Система ломается, потому что identity команды не участвует в записи данных.

Backend видит два HTTP-запроса и считает их двумя независимыми командами создания заказа. `Idempotency-Key` должен определять операцию, а не просто быть декоративным заголовком.

## Исправленная реализация

Исправленная реализация проверяет idempotency key до создания нового заказа:

```python
existing_order = get_order_by_idempotency_key(idempotency_key)
if existing_order is not None:
    return existing_order
```

Только первый запрос создаёт строку. Повтор с тем же ключом возвращает уже существующий заказ, поэтому операцию становится безопасно повторять. В настоящей production-системе это также стоит защищать уникальным ограничением в базе по idempotency key, чтобы выдерживать параллельные повторы.

## Как запустить

Из корня репозитория:

### Сломанная версия

```bash
make broken CASE=BFL-0003
```

Ожидаемо: тест должен упасть, потому что сломанная реализация создаёт дубли заказов.

### Исправленная версия

```bash
make fixed CASE=BFL-0003
```

Ожидаемо: тесты должны пройти, потому что исправленная реализация возвращает уже существующий заказ для повторного ключа.

## Файлы

- `broken/` - реализация, которая игнорирует idempotency key при записи
- `fixed/` - реализация, которая проверяет idempotency key перед вставкой
- `tests/` - тесты, которые проверяют, что повтор команды не создаёт дубли заказов

## Заметки для production

В этом case используется простой повтор HTTP-запроса, чтобы первая версия оставалась маленькой. Та же ошибка встречается в очередях, webhooks, workers и payment flows.

Отдельный future case может добавить Redis, Celery или настоящий retry loop в worker. Главный принцип останется тем же: повторное выполнение одной команды не должно повторять побочный эффект.

В production идемпотентность обычно стоит защищать через долговременное хранилище и уникальное ограничение. Проверка в коде полезна, но база тоже должна защищать invariant.

## Компромиссы

Idempotency key делает retry безопасным, но системе нужно решить, как долго хранить ключи и какие данные запроса привязывать к ключу.

Уникальное ограничение в базе надёжно, но параллельные запросы всё равно требуют аккуратной работы с транзакциями.

Решение только через cache может быть быстрее, но состояние легче потерять после restart, если cache недостаточно надёжен для бизнес-риска.
