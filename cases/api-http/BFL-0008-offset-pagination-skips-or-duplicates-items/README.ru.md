# Offset pagination пропускает или дублирует элементы

## Краткое описание

API использует offset pagination для списка заказов, который постоянно меняется.

Пока данные не меняются, всё выглядит нормально. Если между запросами страниц добавляются новые заказы, вторая страница может вернуть дубликат или пропустить элементы.

## Проблема

В API есть endpoint такого вида:

```http
GET /orders?limit=2&offset=2
```

Endpoint сортирует заказы от новых к старым и применяет `OFFSET`.

Это выглядит просто, но `OFFSET` работает по позиции. Если до запроса следующей страницы вставить новый заказ, позиции всех следующих строк сдвигаются.

## Почему это происходит в production

Offset pagination легко реализовать и объяснить, поэтому она часто появляется в первых версиях API.

Проблема в том, что production-списки редко бывают статичными. Новые строки добавляются, старые удаляются, фильтры могут меняться прямо во время листания. Offset pagination предполагает, что позиции строк стабильны между запросами, но база данных не гарантирует этого для изменяющегося результата.

## Сценарий бага

1. В базе есть заказы `5, 4, 3, 2, 1`, отсортированные от новых к старым.
2. Клиент запрашивает `GET /orders?limit=2&offset=0` и получает `5, 4`.
3. В начало списка вставляется новый заказ `6`.
4. Клиент запрашивает `GET /orders?limit=2&offset=2`.
5. Backend пропускает `6, 5` и возвращает `4, 3`.
6. Заказ `4` появляется на двух страницах.

## Сломанная реализация

Сломанная реализация использует offset pagination:

```python
select(Order).order_by(Order.id.desc()).limit(limit).offset(offset)
```

Из-за этого вторая страница зависит от текущей позиции строк, а не от последнего заказа, который клиент реально видел.

## Где именно происходит ошибка

Ошибка находится в контракте пагинации.

Клиент думает, что `offset=2` означает: "дай следующие элементы после двух уже полученных". База данных понимает это иначе: "пропусти первые две строки в текущем результате".

Когда между запросами появляются новые строки, это уже не одно и то же.

## Как отлавливать такую ошибку

Недостаточно тестировать пагинацию только на неизменяемом наборе данных.

Полезный тест должен повторять реальный поток:

1. запросить первую страницу;
2. вставить более новую строку;
3. запросить вторую страницу;
4. проверить, что страницы не пересекаются и ожидаемые старые элементы не пропали.

Такой тест ловит пользовательскую проблему: дубликаты или пропуски между страницами.

## Падающий тест

Падающий тест читает первую страницу и получает заказы `5, 4`.

Затем он вставляет заказ `6` и читает вторую страницу с `offset=2`.

Безопасное поведение вернуло бы `3, 2`, потому что это следующие более старые заказы после `4`.

Сломанная реализация возвращает `4, 3`, поэтому тест падает.

## Диагностика

Система ломается, потому что offset pagination использует сдвигающуюся позицию как границу страницы.

Граница страницы должна опираться на стабильное значение из предыдущего ответа. Для списка заказов от новых к старым такой границей может быть ID последнего увиденного заказа.

Тогда следующий запрос имеет понятный смысл: вернуть заказы старше последнего заказа, который клиент уже видел.

## Исправленная реализация

Исправленная реализация использует cursor pagination:

```python
select(Order).where(Order.id < cursor).order_by(Order.id.desc()).limit(limit)
```

У первой страницы cursor отсутствует. Ответ содержит `next_cursor` — ID последнего элемента на странице.

Следующий запрос передаёт этот cursor:

```http
GET /orders?limit=2&cursor=4
```

Теперь новый заказ `6` не влияет на следующую страницу, потому что запрос явно просит заказы с `id < 4`.

## Как запустить

Из корня репозитория:

### Сломанная версия

```bash
make broken CASE=BFL-0008
```

Ожидаемо: тест должен упасть, потому что offset pagination дублирует элемент после вставки новой записи.

### Исправленная версия

```bash
make fixed CASE=BFL-0008
```

Ожидаемо: тесты должны пройти, потому что cursor pagination использует стабильную границу страницы.

- `fixed/` - реализация с cursor pagination по ID заказа
- `tests/` - тесты, которые вставляют новый заказ между запросами страниц

## Заметки для production

Offset pagination может быть нормальной для маленьких админок, статичных данных или низкорисковых внутренних инструментов.

Для пользовательских лент, истории заказов, activity logs и других изменяющихся списков cursor pagination обычно безопаснее. Cursor должен строиться на тех же полях, по которым идёт сортировка.

Всегда задавай детерминированную сортировку. Пагинация без стабильного `ORDER BY` может давать непредсказуемые страницы даже без новых вставок.

## Компромиссы

Offset pagination простая и позволяет переходить к номеру страницы, но она становится ненадёжной и медленной на больших изменяющихся данных.

Cursor pagination стабильнее и часто быстрее, но она плохо подходит для произвольного перехода на страницу по номеру.

Cursor только по `id` достаточно прост для этого case. В реальных системах cursor может включать несколько полей, например `created_at` и `id`, чтобы корректно обрабатывать совпадения и сохранять детерминированную сортировку.
