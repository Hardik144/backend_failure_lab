# Lost update при двух изменениях баланса

## Краткое описание

Два запроса почти одновременно списывают деньги с одного аккаунта. Оба читают старый баланс, потом оба записывают новый баланс, и одно изменение теряется.

Этот case объясняет lost update: транзакции вроде бы есть, но код всё равно использует небезопасный read-modify-write паттерн.

## Проблема

У аккаунта есть баланс:

```text
balance = 100.00
```

Два запроса пересекаются по времени:

```text
Request A читает balance 100.00
Request B читает balance 100.00
Request A записывает balance 70.00
Request B записывает balance 80.00
```

Итоговый баланс должен быть `50.00`, но одна запись перетирает другую, и итоговый баланс становится `80.00`.

## Почему это происходит в production

Такой баг появляется, когда код читает строку, считает новое значение в памяти приложения и позже записывает результат обратно.

Когда запросы идут по одному, всё выглядит правильно. Под параллельной нагрузкой две транзакции могут считать новое значение от одного и того же старого баланса.

Балансы, остатки товаров, квоты, места, кредиты и лимиты использования — типичные места для такой ошибки.

## Сценарий бага

1. У аккаунта `#1` баланс `100.00`.
2. Request A списывает `30.00`.
3. Request B списывает `20.00`.
4. Оба запроса читают баланс `100.00` до того, как увидят запись друг друга.
5. Request A записывает `70.00`.
6. Request B записывает `80.00`.
7. Списание `30.00` потеряно.

## Сломанная реализация

Сломанная реализация делает read-modify-write в коде приложения:

```python
account = get_account(account_id)
account.balance_cents = account.balance_cents - amount_cents
commit()
```

Расчёт использует баланс, который был загружен в текущую session. Если другой запрос уже изменил строку, этот код всё равно может записать значение, посчитанное от устаревших данных.

## Где именно происходит ошибка

Ошибка происходит между чтением и записью.

В `broken/repository.py` функция `withdraw()` сначала загружает объект аккаунта, а потом присваивает новый balance:

```python
account.balance_cents = account.balance_cents - amount_cents
```

Это присваивание не является атомарной операцией в базе. Это вычисление в приложении и последующая запись.

Тест специально показывает это через две SQLAlchemy sessions. Обе sessions читают один и тот же начальный баланс до записи. Потом каждая session записывает свой рассчитанный результат.

## Как отлавливать такую ошибку

Обычного happy-path теста недостаточно. Если тест делает два списания строго одно за другим, сломанный код может выглядеть правильным.

Чтобы поймать баг, тест должен смоделировать пересечение операций:

1. Открыть две sessions.
2. Прочитать один аккаунт в обеих sessions.
3. Посчитать два разных новых баланса.
4. Закоммитить обе записи.
5. Проверить, что оба списания повлияли на итоговый баланс.

Главная проверка не в том, что обе операции вернули success. Важно, чтобы итоговый баланс в базе учитывал оба изменения.

## Падающий тест

Падающий тест начинает с баланса `100.00`.

Он моделирует два пересекающихся списания:

- `30.00`
- `20.00`

Безопасное поведение — итоговый баланс `50.00`.

Сломанная реализация заканчивает балансом `80.00`, поэтому тест падает.

## Диагностика

Система ломается, потому что граница транзакции не защищает бизнес-инвариант.

Инвариант такой: каждое успешное списание должно ровно один раз уменьшить сохранённый баланс.

Сломанный код обновляет баланс не относительно текущего значения в базе, а относительно старого значения, загруженного в память.

## Исправленная реализация

Исправленная реализация использует атомарный update в базе:

```python
update(Account)
.where(Account.id == account_id)
.values(balance_cents=Account.balance_cents - amount_cents)
```

Так мы просим базу вычесть сумму из текущего сохранённого значения. Приложение больше не читает баланс, не считает новый баланс в памяти и не записывает устаревший результат обратно. Для этого case atomic update — самый маленький фикс, потому что операция похожа на изменение счётчика.

Для более сложных сценариев в PostgreSQL часто подходит `SELECT FOR UPDATE`: заблокировать строку, прочитать актуальное значение, выполнить проверки и записать результат. Optimistic locking — ещё один вариант, если конфликты редкие и приложение умеет безопасно повторять операцию.

## Заметки для production

В production lost updates часто проявляются нестабильно. Они могут появляться только на пиках нагрузки или когда workers одновременно обрабатывают связанные задачи.

Для PostgreSQL-систем типичные решения — atomic updates, `SELECT FOR UPDATE`, optimistic locking или аккуратно спроектированные idempotent commands. Выбор зависит от того, это простое числовое изменение или большой workflow с несколькими проверками.

Всегда тестируй инвариант, который важен бизнесу. Для баланса итоговое сохранённое значение важнее, чем факт, что каждый отдельный запрос вернул success.

## Компромиссы

Atomic update простой и быстрый для изменений, похожих на счётчики, но становится менее удобным, если бизнес-логике нужно несколько чтений и проверок.

`SELECT FOR UPDATE` явный и хорошо подходит для сложной логики баланса, но держит locks и может снижать throughput, если транзакции медленные.

Optimistic locking не держит долгие locks, но вызывающий код должен правильно обрабатывать конфликты и retries.
