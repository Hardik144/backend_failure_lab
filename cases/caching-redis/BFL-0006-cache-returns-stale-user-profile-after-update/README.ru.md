# Cache возвращает старый профиль после обновления

## Краткое описание

Пользователь обновляет профиль, но API продолжает возвращать старое значение из Redis cache.

В базе данных значение уже правильное. Ответ неправильный, потому что старое значение в cache не было сброшено после записи.

## Metadata

- ID: `BFL-0006`
- Category: `caching-redis`
- Secondary category: `idempotency-consistency`
- Level: `junior`
- Technologies: `python`, `fastapi`, `sqlalchemy`, `redis`, `pytest`, `docker-compose`
- Failure modes: `stale-data`
- Status: `draft`

## Проблема

В API есть два эндпоинта:

- `GET /profile` читает профиль текущего пользователя и кладёт его в Redis cache;
- `PATCH /profile` обновляет имя профиля в базе данных.

Сломанная реализация обновляет базу, но не трогает старое значение в Redis. Следующий `GET /profile` попадает в cache и возвращает устаревшие данные.

Из-за этого в production появляется запутанный симптом: в базе всё правильно, а API отвечает старым значением.

## Почему это происходит в production

Такой баг часто появляется, когда чтение ускорили через cache, а запись реализовали так, будто cache не существует.

Путь чтения и путь записи начинают жить отдельно. Чтение использует Redis, запись обновляет только базу, а cache продолжает отдавать старый снимок данных до истечения TTL или ручной очистки.

## Сценарий бага

1. У пользователя `1` в базе имя профиля `Old Name`.
2. Пользователь `1` отправляет `GET /profile`.
3. Backend читает профиль из базы и записывает `Old Name` в Redis.
4. Пользователь `1` отправляет `PATCH /profile` с `name = "Jhon"`.
5. Backend обновляет базу данных.
6. Redis key всё ещё содержит `Old Name`.
7. Следующий `GET /profile` возвращает `Old Name` из cache.

## Сломанная реализация

Сломанная реализация использует cache-aside при чтении:

```python
cached_profile = redis_client.get(cache_key)
if cached_profile:
    return cached_profile

profile = get_profile_from_database(user_id)
redis_client.set(cache_key, profile, ex=ttl)
return profile
```

Но при обновлении меняет только базу:

```python
update_profile_name(user_id=user_id, name="Jhon")
```

Пропущенный шаг — сбросить cache после успешной записи в базу.

## Где именно происходит ошибка

Ошибка происходит в пути записи, а не в самом Redis.

Redis делает ровно то, что ему сказали: хранит и возвращает значение. Неправ backend, потому что он меняет источник истины, но не удаляет и не обновляет сохранённую копию.

Если значение кэшируется при чтении и меняется при записи, код записи должен явно определить, что будет с cache key. Если оставить key как есть, следующие чтения могут увидеть старое состояние.

## Как отлавливать такую ошибку

Недостаточно отдельно протестировать `GET /profile` и `PATCH /profile`.

Полезный тест должен проверять полный поток read-write-read:

1. один раз прочитать профиль, чтобы заполнить cache;
2. обновить профиль;
3. снова прочитать профиль;
4. проверить, что второе чтение вернуло новое значение.

Именно этот поток ловит пользовательскую проблему: старые данные после успешного обновления.

## Падающий тест

Падающий тест создаёт профиль с `name = "Old Name"`.

Потом вызывает:

```text
GET /profile
PATCH /profile {"name": "Jhon"}
GET /profile
```

Безопасное поведение: последний `GET /profile` возвращает `name = "Jhon"`.

Сломанная реализация возвращает `name = "Old Name"`, поэтому тест падает.

## Диагностика

Система ломается, потому что чтение и запись не согласованы между собой.

База данных является источником истины, но Redis тоже может отвечать на чтение. Как только Redis сохранил снимок профиля, backend должен либо сбросить этот снимок после обновления, либо заменить его свежим значением.

TTL не является стратегией корректности. TTL может ограничить время жизни старых данных, но пользователь всё равно может увидеть неправильный ответ до истечения ключа.

## Исправленная реализация

Исправленная реализация удаляет cache key профиля после успешного обновления базы:

```python
updated_profile = update_profile_name(db, user_id=current_user_id, name=payload.name)
delete_profile_cache(redis_client, user_id=current_user_id)
return updated_profile
```

Удаление key — простой и надёжный вариант для cache-aside. Следующий `GET /profile` не найдёт значение в Redis, прочитает свежий профиль из базы и снова положит его в cache.

Другой нормальный вариант — сразу обновить значение в Redis после записи в базу. В этом case удаление проще для понимания: база остаётся источником истины, а cache заново заполняется обычным путём чтения.

## Как запустить

Из корня репозитория:

### Сломанная версия

```bash
make broken CASE=BFL-0006
```

Ожидаемо: тест должен упасть, потому что сломанная реализация возвращает старый профиль из cache после обновления.

### Исправленная версия

```bash
make fixed CASE=BFL-0006
```

Ожидаемо: тесты должны пройти, потому что исправленная реализация сбрасывает Redis key после обновления.

Для этого case нужен Redis. Docker runner запускает Redis через `docker compose`.

## Файлы

- `broken/` - реализация, которая обновляет базу, но оставляет старое значение в cache
- `fixed/` - реализация, которая сбрасывает cache профиля после обновления
- `tests/` - тесты для поведения read-write-read

## Заметки для production

Сброс cache должен быть частью проектирования записи. Если запись меняет данные, которые может вернуть кэшированное чтение, запись должна удалить или обновить связанный cache key.

Используй стабильные и понятные cache keys. В этом case key выглядит как `profile:{user_id}`, поэтому понятно, какой key нужно сбросить при изменении профиля пользователя.

Не стоит полагаться только на TTL. TTL полезен как запасной механизм, но он не должен быть единственным способом сделать обновлённые данные видимыми.

## Компромиссы

Удаление cache key простое и безопасное, но следующий запрос снова пойдёт в базу.

Немедленное обновление cache экономит чтение из базы на следующем запросе, но дублирует логику сериализации в пути записи и может стать сложнее в поддержке.

Короткий TTL сокращает время жизни старых данных, но увеличивает нагрузку на cache и всё равно допускает неправильные ответы до истечения ключа.
